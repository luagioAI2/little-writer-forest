## 新增：AI 会话「贴图 → 出题 → 确认 → 进题库」流水线

用户想要：在 AI 会话里贴一张/几张图就生成作文题库条目，会话里来回改，
说「确认添加」后进题库。

**结论：文件是唯一通路。** App 的题库在它自己的 IndexedDB 里，
AI 会话碰不到。所以定成：
`AI 写 library-inbox/*.json → 人在 App 题库页点「📥 导入题库」`。

### 落地的东西

- `scripts/inbox-verify.test.ts` —— **收件箱闸门**。拿 `library-inbox/` 里的
  每个 `*.json` 去跑 **App 自己的 `importLibrary()`**（不另写一份校验，
  免得两边规则漂移）。8 项判据，专抓 App 会**静默降级**的错：
  `sceneKey` 不存在、`focus` 值不认识、`wordRange` 形状错、`minGrade` 是字符串、
  空图被丢掉、`/photos/x.png` 文件不在、`http://` 混合内容、id 撞车。
  已用一份故意写坏的文件验证过：8 项全红，报错指名道姓。
- `vitest.config.ts` —— include 加了 `scripts/**/*.test.ts`。
- `package.json` —— 加 `npm run inbox:check`（只跑闸门）。
- `library-inbox/` —— `*.json` 待导入（闸门必检）、`*.draft.json` 草稿（跳过）。
  `example.draft.json` 是可照抄的模板，已验过 10 项全绿。
- `public/photos/` —— 贴的图放这儿，题里写 `/photos/<名>.png`（相对路径
  不会踩 `allowMixedContent: false` 的坑）。代价是打进 APK 会涨体积。
- `docs/library-inbox.md` —— 约定文档（为什么是文件、闸门为什么必须跑、
  字段速查、排错表）。
- `README.md` —— 题库一节加了指向上面两个文档的入口。
- 用户级 skill `essay-library-item` —— 让以后任何会话都能照这套流程走。

### 关键坑（写代码时踩到的）

- **`import.meta.url` 在 vitest 里不是 file URL**（是 `http://` 开头的假地址），
  `fileURLToPath` 会抛 `The URL must be of scheme file`。
  改用 `resolve(process.cwd())`（脚本约定从项目根跑）。
- 数 `sceneKey` 别用 `^\s+'[a-z-]+':` 那种模式 —— 那匹配到的是别处的
  lookup map 键，只数出 93 个。真的 key 在 `SCENES` 里写的是 `key: 'xxx'`，
  一共 **126** 个。用 `grep -oE "^\s+key: '[a-z0-9-]+'"`。

## 追加：支持两种图片入口（贴图 / 图片路径）

用户要求两种都要能接。落地成 `scripts/inbox-photo.mjs`（`npm run inbox:photo`）：

- **贴图** → 图落在 **WorkBuddy 内容寻址 blob 库**
  `~/.workbuddy-ai/blobs/<sha256 前两位>/<sha256>.<ext>`
  （已验证：文件名确实等于内容的 sha256）。
  没有原名、没有顺序，所以 `--recent N` 先列出来，
  **再用 Read 逐张认内容确认**，不能靠哈希名猜。
- **图片路径** → 直接给文件或目录都行。

脚本做三件事：编号命名（`<slug>-1.jpg`）→ 压到合理尺寸 → 吐出可直接粘的
`images` JSON。

### 关键 bug：缩放会把 PNG 撑大（已修）

第一版只做「缩放后写盘」，实测 **828×1792 的 PNG 缩到 739×1600 反而从
591 KB 涨到 680 KB** —— canvas 重编码拿不到原图的压缩优化。
一个号称省体积的工具反而把 APK 撑大，比没有还糟。

修法：算「原图 / 缩放·PNG / 缩放·JPEG」三个候选，**挑最小的**；
都比原图大就保留原图。有透明像素时禁用 JPEG（透明会变黑块）。
再测同一组图：**1106.8 KB → 149.3 KB（省 87%）**，扩展名自动变成 `.jpg`。
加了 `--no-convert`（截图文字多时别转 JPEG）。

- 快路径（<400 KB 原样拷）、缩放路径、`--no-convert` 三条都跑过
- 端到端：`inbox-photo` 收图 → 写进 `library-inbox/*.json` → 闸门 10 项全绿
- 反向验证：把 `imageUrl` 改成不存在的路径 → 闸门变红并指名报出

## 第二轮：APK 启动标题栏 / 图标 / 语音崩溃

用户三条反馈：① 进 APK 先是「一个背景页面 + 写着小笔苗的标题栏」，要能去掉；
② 图标要重做，有设计感有文学感；③ 写作文页点语音直接崩。

### ① 启动标题栏 + 白底

两个原因叠在一起：
- `res/values/styles.xml` 里 `AppTheme` 继承 `Theme.AppCompat.Light.DarkActionBar`
  —— **自带标题栏**的主题；activity 上又写着 `android:label="小笔苗"`。
- `AppTheme.NoActionBarLaunch` 继承 Capacitor 默认的 `@drawable/splash`
  —— 一张「白底 + 蓝色 logo」的图，所以每次打开先白茫茫一片。

修法：基础主题换 `Theme.AppCompat.DayNight.NoActionBar` + 显式关
`windowActionBar`/`windowNoTitle`；去掉 activity 的 label；启动主题改用
core-splashscreen 的 `windowSplashScreenBackground`（#101A16）+
`windowSplashScreenAnimatedIcon`（自己的图标）+ `postSplashScreenTheme`；
`MainActivity` 里 `SplashScreen.installSplashScreen()` 收尾；
`launchShowDuration` 保持 0。11 张 splash.png 全部重画成墨夜底。

另外 `App.tsx` 的 `Splash` 原来硬等 2000ms、还带一组大标题「小笔苗 /
作文森林」—— 那组标题就是用户说的「标题栏」。已去掉标题，等待降到 520ms。

**坑**：XML 注释里不能出现 `--`（`mergeDebugResources` 会报
「注释中不允许出现字符串 "--"」），我习惯用的 `----` 分隔线全踩了。

### ② 图标

`scripts/generate-icon.mjs` 重写：一张 108×108 空间的 SVG（笔尖 + 嫩芽，
「笔苗」的字面意思），一次生成
mipmap 五档 ic_launcher / ic_launcher_round / ic_launcher_foreground、
11 张启动图、`public/favicon.svg`，外加 `icon-preview.png` 给人看。

- **前景层尺寸是 108dp 画布**（= launcher 的 1.5 倍），旧脚本把两者写成同尺寸，
  等于把图放大了 1.5 倍塞进安全区，会糊。
- 自适应图标背景改成矢量径向渐变（`drawable/ic_launcher_background.xml`），
  不再用纯色 `@color/ic_launcher_background`。
- 删掉了 Capacitor 默认的 `drawable-v24/ic_launcher_foreground.xml`。

### ③ 语音崩溃（最重要）

真正的根因有两条，都得修：
1. **打出来的 APK 里根本没有 `RECORD_AUDIO` 权限** —— 权限是 09:31 才补进
   manifest 的，而 APK 是昨晚 23:45 打的。用 `aapt2 dump xmltree` 对着 APK
   查过：只有 INTERNET 和 VIBRATE。
2. **安卓 WebView 里的 `webkitSpeechRecognition` 是「有壳没芯」的**：
   对象存在、底层没有识别服务，`start()` 会把 WebView 拖崩。

修法（分原生 / 前端两半）：
- 新增 `LittleSpeechPlugin.java`：包系统 `SpeechRecognizer`，含运行时权限
  （`@Permission` + `requestPermissionForAlias`）、连续听（一句结束自动续上）、
  沉默/没听清静默重试不上报、`onRmsChanged` 节流成音量事件给波形用、
  放停顿到 3 秒（小孩想词慢）。`MainActivity.onCreate` 里 `registerPlugin`
  —— 必须在 `super.onCreate()` 之前。
- `src/platform/speech.ts`：`getSpeechCtor()` 在原生环境直接返回 `null`；
  新增 `probeSpeechSupport()` / `usesNativeSpeech()`；原生会话的监听
  **模块级只挂一次**再派发给"当前会话"（插件是单例、事件全局广播，
  不这样做上一轮的监听会继续吃下一句，文字重复）。
- **必须先调 `plugin.available()` 再挂监听**：插件没挂上时 Capacitor 的
  `addListener` 既不 resolve 也不 reject（实现里没接 reject 分支），会永久挂起，
  表现为「点了麦克风一直显示在听，什么都没发生」。
- `VoiceComposer`：整条启动链路 try/catch；原生时不再开 `getUserMedia`
  抢麦克风；原生音量事件直接喂波形。
- manifest 补 `<queries><intent><action android:name="android.speech.RecognitionService"/>`
  —— 少了它 Android 11+ 上 `isRecognitionAvailable()` 会假报 false。

### 验证

- `npm run lint` 0 error / 8 warning（既有）
- `npm test` **251 / 251**（新增 `src/platform/speech.test.ts` 6 条：
  原生绝不 new webkitSpeechRecognition、原生事件→回调接线、插件缺失时不抛、
  浏览器路径不受影响）
- `gradlew assembleDebug` 通过，产出新的 `小笔苗-debug.apk`

**测试里踩的坑**：`@capacitor/core` 首次 import 时会往 `window.Capacitor`
写自己的实现，而且它的插件注册表是模块级、跨 `vi.resetModules()` 保留的。
所以假 Capacitor 必须**就地改同一个对象**（不能删了重建），否则
`registerPlugin` 拿到的还是老对象，测试会互相污染。

### 产物核验（aapt2 反查 APK，别只看源码）

源码改完 ≠ APK 里有。用 `aapt2 dump xmltree --file AndroidManifest.xml` 反查确认：

- 权限：`INTERNET` / **`RECORD_AUDIO`** / **`MODIFY_AUDIO_SETTINGS`** / `VIBRATE`
  （旧包只有 INTERNET + VIBRATE，这就是语音崩溃的根因）
- `<queries>` 里 `android.speech.RecognitionService` 在
- `application` → `style/AppTheme.NoActionBar`；
  `activity` → `style/AppTheme.NoActionBarLaunch`（parent `Theme.SplashScreen`，背景 `@color/ink_night`）
- **activity 上没有 `label` 属性**（那个 label 就是用户看到的标题栏文字）
- `classes9.dex` 里有 `LittleSpeechPlugin`；主 JS bundle 里有 `LittleSpeech` 桥接串
- 图标：`mipmap-*/ic_launcher.png`、`ic_launcher_round.png`、`ic_launcher_foreground.png`
  各密度齐全 + `drawable/ic_launcher_background.xml`

产物已覆盖到 `小笔苗-debug.apk`（5.32 MB，md5 `584818e3…`，与
`android/app/build/outputs/apk/debug/app-debug.apk` 一致）。

**教训**：manifest 改了但没重新 `assembleDebug`，装出来的还是旧包 ——
上一轮就是这样漏掉了 RECORD_AUDIO。以后改 manifest 必须重新打包 + 反查。

## 第三轮：把插画换成 App 图标（白底 → 透明 PNG）

用户给了一张 ChatGPT 生成的插画（女孩 + 奶牛 + 农场，圆角方形「贴纸」式），
要求「用它做 ICON，但背景白色换成透明，png」。

原始素材已收进仓库：`assets/icon/source.png`（1254×1254）。
（用户是从 `C:/Users/admin/Downloads/ChatGPT Image 2026年9月16日 11_54_30.png`
拖进来的；剪贴板那份是 200 KB 的 JPEG 转存，别用，要用 Downloads 里
1.7 MB 的原始 PNG。）

### 抠图这一步踩了两个坑，都写进 README 了

**坑 1：不能做「接近白就透明」的全局抠图。**
插画里天空、白云、女孩的白衬衫、鸡、清单纸本身就是白的，全局抠图会在
画面上打出一堆洞。正解是**从画布边框做连通域洪水填充**，只吃掉和边缘
连通的那一圈背景（内部的白因为被画面包住，填不到）。背景也不是纯白，
是 `#FDFCFA` 这种很淡的暖白（实测离纯白距离约 4~7）。

**坑 2（更隐蔽）：不能用「离白色多远」划抗锯齿边缘带。**
第一版就是这么做，结果**天空被抠穿了**：天空的浅蓝离白只有 ~93 的距离，
band 一放宽（140）洪水填充就顺着画面边缘渗进天空，整片天空变半透明
（深色底上一看就是一片黑斑）。而且这时候「最近的内容色」也被算错，
因为天空本身已经被当成背景了。

正解：边缘只能靠**几何**。先用小容差（25）洪水填充拿到轮廓，再对轮廓
做**抗离群点的超椭圆拟合**，由拟合出的隐函数解析地算 alpha。

拟合这里还有第三个坑：**白色的海鸥和云会让洪水填充钻进画面内部**，
于是约 1% 的轮廓点落在画面里面（不是边界），它们会把最小二乘拟合整个
带偏（残差最大 116px）。所以必须迭代重加权：拟合 → 丢掉残差 > 3px 的点
→ 再拟合，直到 inlier 集合稳定。拟合结果 n=3.88，inlier 平均残差 +0.36px。

（顺带确认：这张图的圆角不是普通 rounded-rect，是 iOS 那种连续圆角
/squircle，用圆弧公式去解半径会得到互相矛盾的值 —— 所以必须拟合超椭圆，
不能假设圆角。）

### 图标布局：108dp 里只放 74dp

- 自适应图标画布 108dp，**只有中间 72dp 保证可见**（外面每边 18dp 会被裁）。
  把图铺满 108dp = 白扔三分之一构图（第一版就是这样，女孩的脸糊满整个
  图标，谷仓和风车全没了）。
- 所以图缩到 **74dp 居中**：轮廓在轴向 36dp、对角约 42dp，仍然盖得住整个
  72dp 可见区，而圆形遮罩里看到的是**完整**画面。
- 背景层 = 同一张 74dp 的图把周围透明区**向外边缘延展**（BFS 最近色），
  和前景同比例，万一哪个启动器露出超过 72dp 也能无缝接上。
- **模拟遮罩时别搞错**：遮罩只盖 108dp 画布里中间那 72dp，不是整张画布。
  我第一版把圆形遮罩画成整个 108dp 直径，预览里前景四周露出一圈奇怪的
  拉伸条纹，差点以为图错了。

### 编码选择

- 桌面图标（`ic_launcher*` / `ic_launcher_background` / `_foreground`）：无损 PNG。
  这是 App 的门面，值得。
- splash 图标：WebP q92。同一张 768px，**PNG 769 KB → WebP 111 KB**。
  只出现半秒，看不出差别。APK 因此少 0.66 MB。

### splash 尺寸：两边必须一样大（第四轮补的）

把 App 开场画面换成同一个圆标之后，**两边尺寸其实差 2.25 倍**：

- 系统把 `windowSplashScreenAnimatedIcon` 缩放到
  `splashscreen_icon_size_no_background` = **288dp** 的框里
  （`aapt2 dump resources app.apk | grep splashscreen_icon_size_no_background`
  可直接看到；core-splashscreen 的 compat 布局 `res/layout/splash_screen_view.xml`
  里 ImageView 的宽高就是 `?splashScreenIconSize`）。铺满画布 → 画出 288dp 的圆。
- 而 `App.tsx` 那边是 `h-32 w-32` = 128px = 128dp。

切过去会明显缩一下。按设计规范（画面落在内圈 192dp）改成：
画布 768px、圆内切 **512px（2/3）** → 实际渲染 **192dp**；
`App.tsx` 同步改 `h-48 w-48`（192px = 192dp，viewport 是
`width=device-width, initial-scale=1`，1 CSS px 就是 1dp）。
web 侧标记图从 512px 提到 576px（192×3，够 3x 屏）。

**怎么把这一屏截出来**：开场只挂 520ms，比无头截图还快，直接
「打开 → 截图」拍到的是下一屏。所以
`scripts/icon/capture-splash.mjs` 里用 `evaluateOnNewDocument` 只把那一句
`setTimeout(fn, 520)` 拉长到 60s，别的定时器不动。截图存
`assets/icon/splash-check.png`。

## 第五轮：清掉 Capacitor 自带的那 11 张「白底 + 蓝色 logo」启动图

换图标只改了 `styles.xml` 的引用，**文件本身还留在工程里**。脚手架在
`res/drawable/splash.png` 和 `res/drawable-port-*/`、`res/drawable-land-*/`
下铺了 11 张，共 93 KB。留着是个隐患：那是用户上一轮抱怨过的那张图，
只差一次 `SplashScreen.show()` 调用就会重新露出来。

### 先证明它是死资源（三步都查到源码了）

1. `capacitor.config.json` 里 `SplashScreen.launchShowDuration = 0`
   → `SplashScreen.showOnLaunch()` 第一行就 `if (launchShowDuration == 0) return;`
   → `buildViews()`（唯一会调 `getSplashDrawable()` 的地方）根本不执行。
   注意插件里这个默认值是 **500**，是我们在 config 里显式改成 0 才让它失效的。
2. `getSplashDrawable()` 用的是

## 第 7 轮：录音转文字没出来（两个病因）+ 启动画面太长 + 打包给用户装

用户指令（原话）："你不用UI测试,直接打包APK, 我要安装试试. 另外启动画面的
停留时间有点长. 可以再短一点，现在应该是2秒"。上一条还没解决的是
"写作文录音可以，但录音没转成文字；改作文录音也没用"。

### 病因①：界面在结果到达之前就把文本读走了

`ReciteView.stop()`：`rec?.stop()` 之后 `await sleep(320)` 就去读
`transcriptRef.current`。而系统 `SpeechRecognizer` 的 `onResults`
**不是**在 `stopListening()` 时同步回来的（要等识别服务处理完已收音频），
原生识别会话为此留了 **1600ms** 宽限窗口。`320 < 1600` —— 最后一句
（往往就是全部内容）在到达之前就被读走了。两个数字各写各的，从没对上过。

**修法不是把 320 改大**：写死任何数都会在慢设备上丢最后一句，而丢的
恰恰是孩子刚说的那句，最看不出来也最伤。改成向识别器要约定：
`await rec?.settled()`（真结果到了提前 resolve，慢则等满窗口）。
`src/platform/speech.ts` 里导出 `NATIVE_RESULT_GRACE_MS = 1600` /
`WEB_RESULT_GRACE_MS = 600`，明确写"界面不许自己编数字"。
`speech.test.ts` 6 → 14 条。

**我的第一个假设是错的**：我以为是"迟到结果被丢掉"，写了 3 条测试，
**在未改动的代码上全部通过**，证伪了假设，才转向 320 vs 1600 这条真因。
（教训：先写测试证伪自己，比直接改代码快。）

### 病因②：识别回调没切回主线程（Java 侧）

`LittleSpeechPlugin` 的 `RecognitionListener` 回调
（`onReadyForSpeech` / `onBeginningOfSpeech` / `onRmsChanged` /
`onEndOfSpeech` / `onError` / `onResults` / `onPartialResults`）
是识别服务（另一进程 / binder 线程）打进来的，却**直接调
`notifyListeners`** —— 而 Capacitor 的 `notifyListeners` 最终要在
WebView 主线程上跑 JS。非主线程直接调抛出的异常被
`catch (Throwable ignored)` **静默吃掉**，表现就是"录音在跑、文字一个没有"。
主要坏在 `onResults`（最后一句）上，中间 `onPartialResults` 有时侥幸能过，
所以看上去像"偶尔灵、偶尔不灵"。

修法：7 个回调统一包 `runOnUi(...)`。这个类里**本来就有** `runOnUi`
（`release()` 一直在用），只是事件回调漏了。

**⚠️ 关键教训：这两个故障症状一模一样，必须两个都修。**
只修一个，用户会回来说"还是不行"——而且两次都会觉得"明明改了啊"。

### 改作文为什么本来没坏（但也要修②）

`VoiceComposer`（说作文/改作文共用）从不"按停后去读攒下来的文本"——
每句都走 `onFinal` 回调直接写进正文，所以没有①的 320ms 竞态。
但它同样吃②的亏（`onResults` 一样在 binder 线程发事件）。所以②是共同病根。

### 启动画面：主要成本不在那个 setTimeout

用户感知约 2 秒。`App.tsx:245` 是 `if (!ready || !splashDone)`，
所以可见时长 = `max(Splash 下限, boot() 还没 ready 的时间)`。
**真正的成本是 `boot()`** —— 它是 `Promise.all` 里 **15 条各自独立的
`readXX()`**，每条都是一次 IndexedDB 事务。Android WebView 上
IndexedDB 落 SQLite，每次事务 `BEGIN…COMMIT` 落一次盘（还要过跨进程桥），
一次约 20–40ms，十几次串起来就是 **300–500ms 白屏**，全花在排队等落盘上。

修法：新增 `readBootSnapshot()`，**一个事务**读完首屏所有状态。
关键细节：`meta` 表用 `toArray()` 一次拿全表再建 Map，**不是**十几个键逐个
`get()` —— 每个 `get()` 都是一条**独立请求**。代价是不能再用 `orderBy()`
走游标，改成整表拿回内存排序（数据量小，反而更快）。
`works` 只取 `status !== 'draft'`（`Work.content` 整篇字符串是最大一块，
首屏只列已完成的）。

`Splash` 组件改成 **260ms 停留 + 淡出交棒**（共约 320ms），
画面是"化开"而不是"等够硬切"——所以即使 boot 慢一点也不会读成"卡住了"。
`styles.xml` 的 `AppTheme.NoActionBarLaunch` 加了注释说明：**系统 splash
那一层不受这些参数控制**，停多久取决于 WebView 首帧。

## 第 8 轮：录音转文字**仍然**不行 —— 我上一轮只修了一半

**教训：我第 7 轮宣称"修好了"，但漏掉了第三处病根，而且漏掉的恰是最隐蔽的一处。**

### 第三个病根：会话登记得太晚（`src/platform/speech.ts`）

```ts
start: () => {
  void (async () => {
    await plugin.available()                        // ┐
    await ensureNativeWired(plugin)                 // ├ 三步跨进程调用
    currentNativeSession = { token, cb: cbWithSettle }  // ← 太晚了！
    await plugin.start({ lang, continuous: true })   // ┘
  })()
}
```

`currentNativeSession` 是模块级的"当前会话"，`dispatchNative()` 第一行就是
`if (!session) return`。登记原本在三个 await **之后**，所以启动窗口内到达的
任何事件全被丢掉。其中 `end` 最致命：上层收到 onEnd 会把 recRef 置空、
然后去读一个还没写过的 transcript —— 正是"录了、字是空的"。

而且**不是小概率**：`available()` 已经等了一瞬，而 recorder 拿麦克风更慢
（`VoiceComposer` 里 `await recorder.start()`），用户完全来得及在识别器
就绪前就按停。

### 修法（两条必须一起）

1. 登记提到**第一个 await 之前**。
2. 新增 `ready` promise，`stop()` 等它结算完再转发给插件 —— 否则
   `plugin.stop()` 打进去时原生 `recognizer == null`，`stopListening()`
   被 try/catch 静默跳过，一个字都没听。

### 我怎样确认这次真的修到了（关键方法论）

**先证明测试能失败，再证明它能通过。** 我把 speech.ts 临时改回旧写法，
跑新测试：**在旧代码上失败**（`expected [] to deeply equal [...]`），
再换回新代码：通过。中间还发现**我的第一版测试是无效的** ——
它直接往 `spy.listeners` 里塞回调，绕过了 `dispatchNative`（也就是绕过了
被测的那一层），所以在新旧代码上**都通过**，等于什么都没测。
改成走真实派发路径（用一个卡住的 `available()` 撑开启动窗口，
派事件进 `spy.listeners` 里 speech.ts 自己挂的那个回调）才有效。

**这条要记住：一个在新旧代码上都通过的测试，等于没有测试。**

### 加了可见的诊断行（避免第三轮猜测）

"点一下没反应"有好几种死法，肉眼完全一样。所以录音界面加了一个
**只在出问题时才出现**的诊断行：
- 提示"这一轮没有收到任何识别结果" → 识别服务没送结果（权限/服务/启动失败）
- 提示"收到了识别结果…但没能写进正文" → 识别是好的，坏在写回那一段
- 在听时显示"已收到 N 句"，确认结果确实在进来
正常使用时这两行都不出现。

## 用户设备确认：华为 Mate40 Pro

用户明确说测试机是 **Mate40 Pro**。这条对语音排查很重要，原因：

华为/荣耀（EMUI / HarmonyOS 的 Android 兼容层）上，
`android.speech.SpeechRecognizer` 到底有没有可用的识别服务、
以及它走不走云端，**机型间差异很大**，而且没有 Google 服务。
社区已知问题：华为/荣耀设备上 `setRecognitionListener` 收不到回调
（"假性无回调"）是常见一类。所以"录音有、文字没有"在 Mate40 Pro 上
多了一个设备侧的可能原因，不能只怀疑自己的代码。

**已经做对的一件事（Android 11+ 包可见性）：**
`AndroidManifest.xml` 里有
```xml
<queries><intent><action android:name="android.speech.RecognitionService"/></intent></queries>
```
没有它，API 30+ 上 `isRecognitionAvailable()` 会直接返回 false ——
系统明明有识别服务，App 却以为没有，然后"自动降级成键盘输入"，
看起来就像语音功能没做。**这条已经在包里**（用 aapt2 dump xmltree 反查过）。
Mate40 Pro 视系统版本可能是 Android 10/11/12，这条是必需的。

### 两个必须记住的技术坑

**① FormData 千万不要手写 Content-Type。**
浏览器要在 multipart 后面补 `boundary`，手写会把它弄丢，
服务端只回一句语焉不详的 400。测试里专门钉了
`headers['Content-Type'] === undefined`。**反向验证过**：
注入 `'Content-Type': 'multipart/form-data'` 后该用例立刻失败。

**② `dataUrlToBlob()` 必须用 `atob()`，不能用 `fetch(dataUrl)`。**
Android WebView 把 `data:` 请求当混合内容拦掉。

### 设计上的关键决定：转写成功走**同一个** `handleFinal()`

系统识别和云端转写是同一接口的两个实现，转写完调用的
`handleFinal(r.text)` 就是原来那条路。于是"说作文 → 追加"和
"说修改指令 → 改作文"两条业务逻辑自动都对，没有为云端路复制一份。
**反向验证过**：把 `handleFinal(r.text)` 换成直接追加，2 条用例失败。
