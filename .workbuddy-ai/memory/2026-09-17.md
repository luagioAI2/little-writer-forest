## 语音转写「为什么慢 / 有没有更快的」——量完再回答

用户问：*"为什么速度那么慢。 是什么原因。 转换。有更快的。"*

### 结论先说

**默认的 Qwen3-ASR 已经是目录里最快的，没有更快的可换。**
服务端空闲时这条路 **中位 419ms**，一点都不慢 —— 所以「慢」不来自模型。

### 证据

**① 模型目录穷举**：`/v1/models` 共 94 个，语音相关 6 个（`CosyVoice2` 是 TTS 不算）
→ 5 个 ASR 全打过。Qwen3-ASR **791ms** 最快；
Ultra 1532 / XingChen 1965 / SenseVoice 8430（2 次挂 1，另一轮 **48.7s**）/
Diarize 19742（2 次挂 1，另一轮全挂）→ 最慢 **25×**。

**② 时长阶梯**（1/2/4/6 份音频）：5.4s→683ms · 10.9s→1090ms · 21.7s→2791ms · 32.6s→5743ms
→ 拟合 **≈100–190 ms × 音频秒 + 固定开销**。斜率是推理成本，**客户端优化不了**；
真正的杠杆是「一次只说一句话」。

**③ 连打 15 次（webm/opus，App 真发的格式）**：330 / 372 / 373 / 390 / 396 / 404 /
412 / 419 / 433 / 456 / 519 / 558 / 602 / 651 / 652 ms
→ 最快 330 · **中位 419** · 最慢 652 · 最慢/最快 2.0×。**正常就是 0.4 秒。**

> ⚠️ **跨轮数字不可比。** 同一个模型同一段音频，第一轮 Qwen 887ms、第二轮 791ms，
> 而 WAV 那格第一轮 1398ms、第二轮 **3936ms**。服务端负载波动很大。
> 教训：基准结论只能在同一轮内比较，别把不同时间跑的数字拼成一张表。

### 修掉的一处：第一次超时写死 60 秒

`transcribeWithRetry` 原来是 `timeouts = [60_000, 12_000, 12_000]`。
服务端**会偶发完全不理人**（Diarize/SenseVoice 实测挂过），于是碰上一次抖动
就要让孩子盯 60 秒，而重试通常 0.4 秒就回来 —— **最坏是最佳的 150 倍**。

改成 `firstTimeoutMs(durationMs)`：
```
预算 = 10s 固定 + 0.5s × 音频秒   （下限 12s，上限仍是 60s）
5s→12.5s · 10s→15s · 30s→25s · 60s→40s
```
0.5s/音频秒 ≈ 实测推理成本（0.13–0.19s/音频秒）的 3~4 倍；固定 10s 覆盖
建连+上传+回包（实测合计 <0.5s，留 20 倍余量给弱网）。
补了 2 条单测（用 fake timers + 永不 resolve 的 fetch 模拟「服务端不理人」），
**反向验证过**：装回 `60_000` 两条立刻红（`expected 1 to be 2`）。

### 两个新发现的坑（都写进代码注释了）

**① 服务端信「文件名后缀」，名字和内容不一致 → HTTP 500。**
同一段 webm 二进制只改文件名：`audio.webm`→200 ✅ / `probe.wav`→**500**（稳定复现）；
反向（wav 内容 + `.webm` 名字）→200 ✅（这种它能嗅探）。
`guessFileName()` 原来注释写「服务端多半会 sniff 内容而不是只看名字」——**假设被推翻**，
它是**必须对**，不是「更稳的做法」。加新录音格式时必须同时加映射。
写基准时就真踩了：第一版 `timeOnce()` 里 `fileName` 写死 `'probe.wav'`，
webm 顶着 `.wav` 名字发出去 → 整节假红。

**② 格式不是瓶颈，反而是优势。**
基准前两节用 WAV，但 App 录的是 **webm/opus 16kbps**：
234.2KB vs 10.4KB（小 22.6×）。实测同段人声：WAV 741ms vs webm **240ms**（快 3×）。
→ 编码格式上没有任何可做的。

## 「推荐更快的」——把一次转写拆开量，然后按性价比排

### 关键实测：握手占了四成多

`scripts/_probe-latency.mjs`（同一段 5.44s 人声，各 6 次）：

| | 中位 |
| --- | --- |
| ① 冷连接（每次重新握手） | **375ms** |
| ② 热连接（复用同一条） | **214ms** → 握手 **161ms** |

服务端部分（214ms 里）只跟音频长度和负载有关，**客户端改不动**。
所以客户端唯一能拿的就是这 161ms —— 而它是**可以完全藏起来**的：
按下按钮到松手有 2~10 秒，足够握手。

### 做了：`warmUpTranscribe()`

- 按下「按住说话」时发 `GET {baseUrl}/models`（不消耗转写配额、不留识别记录），
  与说话**并行**跑，不占等待时间。失败静默（`.catch(() => {})`）。
- 调用于 `VoiceComposer.beginHold()`，`useCallback` deps 补了 `transcribe`。
- 只对**本次会话第一次**有效 —— 浏览器 keep-alive（实测 HTTP/1.1 + 连接复用），
  后续本来就热。但第一次最影响观感。
- 4 条单测；「失败必须静默」一条**反向验证过**：拿掉 `.catch()` →
  `预热失败不该冒出未处理的拒绝: expected [Error: 网络炸了] to have length of +0 but got 1`。
  ⚠️ 教训：只断言 `not.toThrow()` 是**假绿** —— 返回 promise 的函数
  漏掉 `.catch()` 不会同步抛，而是变成未处理拒绝。必须监听 `unhandledRejection`。

### 推荐的其它三条（都**没实测过**，如实标注）

  （原生依赖 + 几十~几百 MB 模型 + 机型性能差异）。

### 三个 curl 探针的坑（写进 `_probe-latency.mjs` 注释了）

1. `-o '/dev/null'` 经 `execFileSync` 直接传给 Windows curl 时**不经过 MSYS
   路径转换** → curl 当成 `E:\dev\null` → exit 23。要用 `node:os` 的 `devNull`。
2. `-o` 是**按位置**匹配 URL 的：N 个 URL 就要 N 个 `-o`，否则第 2 个起响应体
   直接打到 stdout，把耗时行搅乱。
3. `-w` 的格式串**结尾必须有 `\n`**：一次 curl 带多 URL 时 `-w` 每个 transfer
   输出一次，没换行就首尾相连挤成一行 → 「N 次」看起来只有 1 行（极隐蔽）。

| 假线索 | 实测结果 |
| --- | --- |

**真正的规律**：只有当这个编译任务**真的需要编译**时才失败；
它 up-to-date 的时候怎么跑都过。
另外 `--rerun-tasks` 强制重编是**成功**的 —— 证明工具链和 Java 21 源码都没问题。

顺带查到的环境事实：`tasklist | grep -i java` 能看到 daemon；

### 为什么要做

## 又补一个盲区：设备路径（连上手机之后那段）从来没验过

`verify-device.mjs` 有三条路径：`--dump`（验过）、无设备（验过）、
**有设备（没验过）**。第三条恰恰是用户真跑的那条。

### 顺手抓到一个真 bug

`listDevices()` 原来只认 `serial\tdevice`，其余全落到"没有连上手机"那句提示上。
但 `adb devices` 有三种状态：

| 状态 | 真实含义 | 该做什么 |
| --- | --- | --- |
| `device` | 能用 | 继续 |
| `unauthorized` | 插着，但**手机屏幕上的授权弹窗没点** | 看手机点"允许" |
| `offline` | 线接触不良 / 设备重启中 | 换线换口 |

最常见的情况（插着、弹窗没点）被引去"检查数据线和 USB 调试开关" ——
**提示指错方向比不提示更费时间**。

### 改了什么

- 把解析抽成纯函数 `parseDevices(stdout)` → `{ ready, unauthorized, offline }`，
  排掉 `List of devices attached` 和 `* daemon ...` 噪声。
- 新增 `noDeviceHint({ unauthorized, offline })`，按"卡在哪一步"给不同的提示。
- 认不出来的状态（如 `recovery`）**不进 ready** —— 宁可不认，也不能乱用。

### 为什么只测纯函数、不测整条设备路径

本来想用假的 `adb` 顶掉 PATH 来端到端跑，但 Windows 上 `execFileSync` 不能直接执行
`.cmd`/`.bat`（Node 的安全限制），而没有扩展名的脚本又不走 PATHEXT —— 做不干净。
所以测两个纯函数（分支都在这里），设备路径的"接线"（两行）靠人工跑无设备路径确认。
**这是残留的缺口，写下来免得下次以为是全覆盖。**

## 火山引擎流式识别：实测完了（用户给了真 key）

上一节说「没凭据、没实测」。用户随后给了真 key
（`21c1051f-…`，配 curl 打的是 `volc.seedasr.auc` 录音文件识别），于是补完了。

### 一、先量「录音文件识别」（异步两段式）

写了 `scripts/_probe-volcengine.mjs`（submit + query 轮询，读 WAV 头声明 rate/bits/channel）。
同一段 `speech_probe.wav`（5.437 s、22050Hz 单声道）跑 3 次：

| run | submit | 提交→就绪 | 轮询次数 |
| --- | --- | --- | --- |
| 1 | 591 ms | 1803 ms | 3 |
| 2 | 437 ms | 2308 ms | 5 |
| 3 | 391 ms | 2078 ms | 5 |

中位 **2078 ms**（上界 —— 结果可能在两次轮询之间就绪）。文本正确。
**踩坑：`20000001 [Processing in progress]` 是正常中间态，不是错误。**
一开始只认 `20000000`，第一次轮询就退出并报"query 失败"，把正常态当成了故障。

### 二、再量「流式」（这才是用户真正想要的）

★ 关键认知：**「流式」不是一种东西。** 火山有三个流式端点，收益差一个数量级。
写了 `scripts/_probe-volcengine-stream.mjs`（v3 二进制帧，原生 `ws` 支持握手头）。

统一指标定成「**松手 → 出字**」（用户视角），四种形态横向比：

| 形态 | 协议形状 | 松手→出字 | 首字出现 |
| --- | --- | --- | --- |
| 硅基流动（现状） | 整包上传 | 419 ms | 松手后 |
| 火山 录音文件识别 | 异步两段式 | **2078 ms** | 松手后 |
| 火山 单向流式 `bigmodel_nostream` | 边说边传，整句返回 | 348 ms | 松手后 |
| 火山 双向流式 `bigmodel` | 边说边传，边说边出字 | **−4371 ms** | 开口后约 1.1 s |

三个反直觉结论：
1. **异步两段式是陷阱** —— submit 只要 437 ms 就返回 200，但那只是"任务收下了"。
   量到 submit 就汇报会得出好看但**错误**的结论。异步接口必须量到最终结果。
2. **单向流式几乎不解决问题** —— 它只把「上传」挪出关键路径，而上传本来就不是瓶颈
   （几十 KB）。识别时间一分没少，只快 17%。
3. **只有流式输出（双向）才是质变** —— `−4371 ms` 这个负数**不是 bug 是成功信号**：
   结果跑到用户动作前面去了，关键路径上什么都没剩，松手后只剩 150 ms 收尾。
   顺带验证官方那句「单向流式 5 秒音频 300~400ms」—— 实测 348 ms，**它没吹**。

`async` 端点：−4363 ms / 终稿中位 202 ms，与 duplex 同级。

### 三、两个协议坑（都很隐蔽）

1. **「最后一包」靠标志位表达，不是 finish 事件。** v3 帧里
   `flags=0b0010/0b0011` 才是"最后一包"。忘了设 → 服务端一直等你发音频，
   表现成「连上了、也发了、就是没结果」，很容易误判成服务不可用。
2. **★ 官方示例的响应结构和线上报文不一致。** 官方文档写
   `{ payload_msg: { result: { text } } }`，线上真实报文**没有 `payload_msg` 这层信封**：
   `{ audio_info, result: { additions, text } }`。
   照文档写的提取器**不报错**，只是永远拿到空字符串 —— 表现为"帧都收到了、就是没文本"。
   → 教训：**先 dump 原始帧，再写提取器**；提取器同时兼容两种形状。

另外：分包 100 ms vs 200 ms → **包数翻倍而耗时不降**（300 vs 150 ms 中位，n=2 噪声内），
照官方推荐值走。

### 四、对决策有用的几点

- **密钥对三个流式端点都通**，不用另外开通服务。
- 识别文本与硅基流动**逐字一致**（`我家有一只小猫，它很喜欢在阳台上晒太阳。`）。
- 双向流式**不需要新做界面** —— `VoiceComposer` 已有 `interim` 状态和显示行
  （`{interim || ...}`），只多一条"往 `setInterim` 喂字"的通路。
- 代价：**要改采集链路**（`MediaRecorder` 出 webm/opus，流式要 PCM → `AudioWorklet`）
  ＋ **¥2.2 / 小时音频**（从 ¥0 起）。
- **还没做的**：真机实测（无硬件）；`ByteDance-Seed/Seed-OSS-36B-Instruct` 那条线未动。

### 五、沉淀

- README 的「③ 换成流式」整段重写（原文写着"没凭据、没实测过"），
  并把四种形态的表加进验收状态。

  收益差一个数量级」** —— 这个教训是通用的：**最大的延迟收益往往来自把工作

## 把火山流式接进 App（默认引擎 + 打包）

用户说「默认帮我填好 字节的。打包给我测试下。」= 上一轮那个"要不要上流式"的决定：
上，并且做成**默认**。

### 一、★ 决定架构的那次探测：浏览器根本连不上

写任何 App 代码之前先问了一句「浏览器能不能连」——答案是**不能**。

`WebSocket` 构造函数**没有设置请求头的能力**（`new WebSocket(url, protocols)`，
WHATWG 规范就没这个参数，不是 WebView 的毛病）。而火山 v3 鉴权全在握手头里
（`X-Api-Key` / `X-Api-Resource-Id`）。两条绕行路都试了，`scripts/_probe-ws-auth.mjs`：

```
① 查询串 api_key/resource_id     → 403  get resource id empty
① 查询串 头名原样 X-Api-Key      → 400  get resource id empty
① 查询串 apiKey/resourceId       → 400  get resource id empty
① 查询串 只带 key                → 403  get resource id empty
② 子协议传 key                   → 400  get resource id empty
```

服务端**只从请求头读 resource id**。所以：**纯 WebView 的流式客户端物理上做不到**，
socket 必须放在原生。

（顺带记一条线索：火山的 CORS `access-control-allow-headers` 里有
`X-Api-App-Key` / `X-Api-Access-Key`，**没有** `X-Api-Key` —— 老的 app-key 体系
理论上能走浏览器，新控制台的 key 不行。没试，留个话头。）

### 二、架构（四层，协议全在 TS 里）

| 文件 | 职责 |
|---|---|
| `android/.../VolcWebSocketPlugin.java` | OkHttp，**只做字节管道**，不含任何协议知识 |
| `src/platform/ws-transport.ts` | 传输抽象（原生/浏览器两条实现） |
| `src/platform/volcengine.ts` | **纯协议层**（组帧/解帧/取文本），不碰 socket → 可单测 |
| `src/platform/pcm-capture.ts` | Web Audio 采 PCM |

这么切的原因：**这条链路在桌面上跑不起来**，只有把协议和传输分开，
协议才测得了。为此写了 `volcengine.test.ts` **21 条**测试 —— 其中一条当场抓到
`extractText` 没解 `payload_msg` 信封的真 bug（断言 `expected '' to be '您好'`）。

### 三、实现上的三个坑（都写进 README 了）

1. **「最后一包」是标志位，不是 finish 事件**（`flags=0b0010`）。不发它服务端永远等音频。
2. **`webm` 流式端点不收**：`45000151 unsupported format webm`。
   → 所以不能用 `MediaRecorder`，得用 Web Audio 采 PCM。
   收的格式：wav/mp3/ogg/pcm/spx/amr/aac/m4a。
3. **先开麦，再等建连**。反过来的话开头半个字会丢在建连的 ~200ms 里。
   做法：`capture.start()` 和 `openVolcStream()` 并行，连上之前的音频先攒在
   `earlyChunksRef`，连上后补发。

其他防守：`crypto.randomUUID` 兜底（老华为 WebView 没有）；`ctx.state==='suspended'`
时 `await ctx.resume()`（否则 `onaudioprocess` 一次都不触发）；握手 8s 看门狗
（`addListener` 在插件没注册时**既不 resolve 也不 reject**，会永久挂住 —— 这个
失败形态本项目在 `LittleSpeechPlugin` 上已经吃过一次）。

### 四、默认值

`defaultTranscribeConfig()` 现在返回火山 + **内置密钥**（`VOLC_TEST_API_KEY`）。
`openAiTranscribeConfig()` 保留硅基流动那条（桌面端 + 免费备选）。

⚠️ **密钥是编进 APK 的，等于公开** —— 自测没问题，**对外发之前必须改成构建期注入**。
这条注释写在 `transcribe.ts` 里了。

设置页做成双模式卡片：路由开关（火山·边说边传 / 硅基流动·免费）+ 三选一
（duplex / nostream / async）。**桌面端打开会明确警告"这条路只在手机 App 里能用"**，
并说明原因（头设置不了，查询串/子协议实测被 403/400 拒）。不静默降级。

## 出包前的代码审查：抓到 3 个真机上极难定位的 bug

APK 交给用户之前把流式那条路**从头审了一遍** —— 理由是这条链路在桌面上
跑不起来，我唯一没法自测的代码就是它。审出 3 个 bug，全是同一族：
**资源已经建好、但没人再引用它**，症状都是"不报错、只是结果不对"。

### ① 每次松手都吃掉尾巴（`endHold` 顺序写反）

```ts
volcRef.current = null          // ← 先清了
const ok = pcm?.stop()          // stop() 内部 flush(true) 最后一包
// 而 onChunk 靠 volcRef.current 判断"连上了没"
// → 这一包被当成"还没连上"塞进 earlyChunksRef，**永远发不出去**
```

丢 0~200ms（平均约 100ms），中文语速下约等于**最后一个字**。
**每次松手都会发生**，且不报错 —— 真机上只会表现为"有时候结尾少个字"，
几乎必然被归因到"网络不好"或"识别不准"。
修：**先收采集、再清引用**。

### ② `finish()` 早于 `open` 事件 → 最后一包永远发不出

原生插件是先 `c.resolve()` 再 `emit("open")`，**两条各自独立的桥消息，
先后没有保证**。所以在"连接已算成功、opened 还是 false"这个窄窗口里松手，
`finish()` 没东西可发，onOpen 之后也**不会补**最后一包 ——
服务端一直等音频，用户**白等满 20 秒**才看到超时（音频其实早就到了）。
修：记 `finishRequested`，onOpen 里补发。

### ③ 麦克风开失败时，已经在连的 socket 被丢在地上

`openVolcStream()` 在 `await capture.start()` **之前**就发起了，
麦克风失败走 catch 时没人收这条连接 —— 既漏一条连到火山的 socket
（只能等服务端自己超时），又会变成未处理的 rejection。
修：建连 promise 提到 `try` 外面，catch 里 `.then(s => s.cancel()).catch(() => {})`。

### ④ 顺手加的两道护栏

- `lastPacketSent` —— `finish()` 可能被调两次（松手 + 卸载），
  重复的结束信号服务端会当成协议错。
- `configSent` + **出站缓冲 outbox** —— 见下。

### ★ 写测试时又逼出第 4 个：配置帧被静默丢掉

用假传输复刻**最坏时序**（onOpen 早于 transport 赋值）时，测试直接红了：
那一刻 `sendFrame` 里的 `transport?.send(...)` 是**空操作**，
于是**配置帧**（写着 `pcm/16k/单声道`）根本没发出去 ——
服务端不知道我们发的是什么，报的错完全指不到这里。
修：`sendFrame` 在没有 transport 时先攒进 `outbox`，赋值后**按原顺序**补发。

> 这个 bug 是我自己写的假传输"故意摆出最坏时序"才暴露的。
> **如果按理想时序写桩（连接好了再给 handle），测试会全绿。**
> 这是本轮最值钱的一条方法论。

### 验收

- `tsc -b --noEmit` 干净；ESLint **0 error**（8 条既有 warning）。
- 测试 **379 通过 / 10 跳过**（上轮 375，+4 条全是这次新加的时序测试）。
- 新增 4 条测试都在**旧代码上先跑到红**才动手改的。
- 重新出包（修复必须进包，否则用户测的还是带 bug 的那版）。

### 沉淀

`frontend-verify-layers` skill 补了 **§18「链路在本地根本跑不起来时」**：
拆出可测的协议层（协议层一行 socket 都不许有）、
**假传输必须复刻最坏时序而不是理想时序**、以及"静默丢弃"三兄弟的修法。
同时在 §17 的构建纪律里补了"**容忍某一步失败就必须显式校验它的产物还在**"
—— 那条 `cordova.variables.gradle` 报错有**两种**成因，这是第二种。

### 打包脚本那个坑：从"拦住"升级成"自己扛住"

上面写的那道检查**第一次实跑就生效了** —— 打包时 `cap update` 又失败
（这次报的是安全删除垫片的 `genie-trash ... ETIMEDOUT`），
两个文件又没了，脚本**拦下来并给出可操作提示**，而不是让 Gradle 报假错。
所以那道检查是对的，但它只做到"早失败"，代价是**每次都得人工跑一遍 update**。

根因看清楚了：Capacitor 的 `removePluginsNativeFiles()` 是**先删后建**，
删完就失败 = 文件没了、重建也没发生。所以正确做法不是"失败了就停"，
而是**先备份、失败后原样放回**：

```bash
PLUGIN_BACKUP="$(mktemp -d)"
for f in build.gradle cordova.variables.gradle; do
  [ -f "$PLUGIN_DIR/$f" ] && cp "$PLUGIN_DIR/$f" "$PLUGIN_BACKUP/$f"
done
if ! npx cap update android; then
  ...  # 把备份补回去，并说明补了什么
fi
```

保留原来的存在性检查做**兜底**（备份也没得补的情况：第一次跑，
或者跑之前文件就已经不在）。

**这段逻辑单独离线验过**（造一个假目录 → 删空 → 走还原 → 查内容），
因为"只在 update 失败时才走"的分支没法自然复现 —— 而验证工具自己也会说谎。

> 一般化的教训：**决定容忍某一步失败时，要么能证明它的失败是可观测的，
> 要么就把它本该产出的东西先留一份。** 只加"失败就停"是次优解 ——
> 它把一个自动能修的问题变成了必须人工介入的问题。

## 真机验收脚本：让它认识流式那条路

用户马上要真机测，而 `verify-device.mjs` 是照**旧的整包上传链路**写的：
它等的是 `麦克风已打开` / `开始录制` / `录音结束`，而流式打的是
`PCM 采集已启动` / `流式已连上`。默认配置现在就是流式 ——
所以第一次跑验收，它会指着「按下按钮 / 拿到麦克风」说没通过，
把人引去查权限和按钮。**提示指错方向比不提示更费时间。**

改动：
- 加 `isStreaming` 判定（有 `流式*` / `PCM 采集` 就是流式；
  只有「麦克风打开失败」这种**两边共用**的日志时，按默认配置算流式）。
- 两条链路各自的 CHAIN，输出里标明走的是哪条。
- 补 9 个流式专属的失败分支（插件没注册 / 403 / 错误帧 / 终稿超时 /
  没连上就松手 / 采集到 0 个采样点 …），每条都指到具体动作。
- 成功分支认流式的日志形状，并报出**首字时间**（负数 = 松手之前就上屏）。

### ★ 写的时候自己踩了一个，正是要消灭的那个错

CHAIN 里我把失败日志放进了 `or`，等于"算作走到了"：

```
✓ 连上语音服务
✖ 边说边传（松手发最后一包）   ← 断在这里     ← 连接明明失败了
```

**判据定成：只有这一环真的成功了才算 hit，失败日志一律不进 or。**
这样「← 断在这里」才落在真正出问题的那一环。
（整包上传那条链的最后一环把终止态放进 or 是另一回事 ——
它的最后一环本来就叫"服务端回话"，回什么都算走到了那一步。）

另外 `流式终稿超时` **含有** `流式终稿` 这个子串，必须用 `not` 排掉，
否则超时被当成"拿到了终稿"，断点被推到下一环。同类坑之前踩过一次
（`录音结束但没有音频` 含 `录音结束`）。为此加了 `lastOfExact`。

### 验收

- 测试 **391 通过 / 10 跳过**（上轮 379，+12）。
- 按纪律**先看着它红一次**：临时把 `isStreaming` 钉成 false，
  3 条 ★ 测试立刻失败；恢复后全绿。
- 合成了两份日志实跑，确认输出读得通、断点指得对。
- `scripts/` 不进 APK，所以**不需要重新打包**。

## 排查「改作文」：不是没实现，是两个别的问题

用户报「改作文有些问题，好像功能没实现。可能要结合语音转文字，
再加已写好的文章，去大模型修改」。查下来结论完全不同：

### 一、改作文**是完整实现的**，而且刻意不走大模型

`src/domain/voiceEdit.ts` 顶部抄着需求原文：
「编辑的**绝不允许** AI 帮改写。必须是小孩自己的能力。」
职责划分写得很清楚：✔ 找出「棍子」换成「竹签」 ✘ 替孩子想更好的词。

链路完整：模式切换（说作文 / 改作文）→ `parseEditIntent` → `applyEdit`
→ 多处匹配给候选 → 撤销。`allowEditMode` 默认 true，没人在别处关掉。

### 二、真 bug：解析器对**自然口语**很脆

拿真实说法喂进去（探针已删，结论记这里）：

| 说的话 | 结果 |
|---|---|
| 小猫改成小狗 | ✅ 小猫→小狗 |
| 我觉得小猫改成小狗更好 | ❌ 抓成「我觉得小猫」→「小狗更好」 |
| 我想要把小猫改成小狗 | ❌ 抓成「我想要把小猫」 |
| 能不能把小猫改成小狗 | ❌ 抓成「能不能把小猫」 |
| 嗯……小猫改成小狗 | ❌ 抓成「嗯……小猫」 |
| 小猫改成小狗，嗯，就是这样 | ❌ 改成「小狗，嗯，就是这样」 |

**前缀/后缀语气词会让它抓错片段**，然后报"找不到" —— 看起来就像没实现。
而 ASR 输出的正是这种带语气词、带标点的文本，所以真机上很容易撞上。

### 三、另一个更可能被误读成"没实现"的地方：点评

项目**已经有**完整的大模型能力（`src/domain/ai.ts`，OpenAI 兼容
`chat/completions`，还有 `scoreAndRewrite` = 评分 + 生成范文）。
但 `defaultAiConfig()` 是 `mode: 'local'` + `apiKey: ''`，
于是 `shouldUseRemote()` 为假 → **静默走本地引擎**，只给一句
「AI 设置里还缺密钥，先用了本地引擎」的 warning。
默认 baseUrl 是 DeepSeek，预设里还有 Qwen / 智谱。

→ **"看起来没实现"最可能就是这里：大模型那条路一直没配密钥。**

## 改作文接大模型（★ 一次需求变更，不是实现细节）

家长在选项里明确选了「大模型直接改写」。这条**推翻了项目最初的原则**，
所以到处都留了痕，不悄悄删。

### 一、改了什么、为什么改

原原则（`voiceEdit.ts` 顶部抄着原话）：
「编辑的**绝不允许** AI 帮改写。必须是小孩自己的能力。」

推翻它的实证理由：本地精确替换对自然口语很脆 ——
「我觉得小猫改成小狗更好」被抓成「我觉得小猫」→「小狗更好」，
然后报"找不到"。而**语音识别的输出恰好就是这种带语气词、带标点的文本**，
所以真机上很容易撞上，看起来就像功能没实现。

新底线：**AI 只按孩子说出的指令改，不替他想、不扩写、不许自作主张。**
三条硬约束写进 `REVISE_SYSTEM`，并在 `ai.test.ts` 里**用测试钉住** ——
提示词没有类型、没有编译期检查，是最容易被"顺手优化"掉的东西，
改掉它等于悄悄改需求。

### 二、实现

| 位置 | 做了什么 |
|---|---|
| `domain/ai.ts` | 新增 `reviseEssay()`：原文 + 孩子那句话 → 改好的全文 |
| `domain/voiceEdit.ts` | 新增 `changedSpan()`：抠出真正变化的那一段 |
| `domain/voiceEdit.ts` | `revisionPraise(count, aiCount)`：**不再冒领功劳** |
| `domain/types.ts` | `EditOperation.by?: 'child' \| 'ai'` |
| `components/VoiceComposer.tsx` | 编辑模式按 `shouldUseRemote(ai)` 自动选路 |
| `features/compose/ComposePage.tsx` | 透传 `settings.ai` |

本地那条路**保留**：既是 AI 没配好时的兜底，也是「孩子自己动手改」那条路。
降级是静默的（改作文是核心玩法，不该因为没配 AI 就整个不可用），
但效果差异是已知代价。

### 三、★ 顺手修掉的三处"对孩子说假话"

接了大模型之后，界面上一批原本正确的文案全变成了假话：

1. `revisionPraise(1)` → 「**你自己**改了一处，这就是进步」
2. 修改记录标题 → 「**你自己的**修改 · N 处」
3. 每一行看不出是谁改的

现在：记 `by: 'ai'`，文案分三种（全自己 / 全 AI / 混合），
AI 那几行右侧标「AI 按你说的」。
孩子做的是"决定改哪里"，这份功劳照认，但**话得说准**。

### 四、验收

- 测试 **413 通过 / 10 跳过**（上轮 391，+22：ai 11 + voiceEdit 11）。
- `tsc` 干净；ESLint 0 error。
- 按纪律验红：把 `next === original` 那道守卫去掉，

## 续：把「光填密钥不生效」这个坑堵死 + 设置页三句假话

上一节留下的坑是：`shouldUseRemote` 要求 `mode === 'remote'` **而且**密钥非空。
只填密钥、mode 还是 `'local'`，整条大模型链路一声不响地关着 ——
界面看着"配好了"，实际走本地启发式，**没有任何报错**。
这就是「改作文好像没实现」的根因，而且它会**再次发生**（家长照着设置页填完就以为开了）。

### 一、让「填密钥」和「开远程」不可能再分家

`src/domain/ai.ts` 加了内置密钥常量，做法和火山的 `VOLC_TEST_API_KEY` 完全一致：

```ts
export const AI_TEST_API_KEY = ''   // ← 把 DeepSeek 的 key 填这一行

export function defaultAiConfig(): AiConfig {
  return {
    // ★ 不写死 'local'：填了 key 就自动走远程
    mode: AI_TEST_API_KEY ? 'remote' : 'local',
    baseUrl: 'https://api.deepseek.com/v1',
    model: 'deepseek-chat',
    ...
  }
}
```

`baseUrl` / `model` 本来就预置成 DeepSeek 了，所以**家长只需要给一把 key**。
留空 = 行为与之前**逐字节等价**（`'' ? 'remote' : 'local'` 就是 `'local'`），
所以这个改动是零风险的，可以先合进去等密钥。

### 二、★ 先看着它红一次

新加的守卫断言是**关系**而不是取值，这样密钥为空时也成立：

```ts
expect(shouldUseRemote(c)).toBe(c.apiKey.length > 0)
```

注入回归验证过两次：
1. key 非空 + `mode: 'local'` 写死 → **★ 立刻红**（`expected false to be true`），
   正是它要拦的那个 bug。
2. key 非空 + mode 由 key 推导 → 全绿，`shouldUseRemote` 自动变 true。
然后还原（key 回到 `''`）。

`src/domain/ai.test.ts` 11 → **15** 条。

### 三、设置页有三句话在改完需求之后变成假话了

改作文现在真的会改写正文，所以下面这句**已经不成立**：

- ❌ `AI 只负责点评和示范，永远不会替孩子改写作文。`
  → ✅ 改成：「改作文时，AI 只按孩子自己说的那句话动手：最小改动、不扩写、
     不换他的用词。听不懂就直说，不会自己乱改。」

另外两句是**低估**，会让家长测不出功能：

- `sub="配好了，点评会更细腻"` → 「配好了：点评更细腻，改作文也听得懂大白话」
  （只提点评，家长不会想到改作文的引擎也换了）
- 本地模式描述「效果稳定但比较朴素」→ 说清本地模式改作文**只认「把 X 改成 Y」句式**，
  孩子说得随意一点就会认错。这句直接对应家长最初抱怨的"有些问题"。

这三句合起来才是"家长装完能自己判断有没有生效"的最小信息量。
