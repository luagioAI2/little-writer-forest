## 一、修「设置了名字，再选择头像，名字就清除了」（家长报，说之前没修好）

### 现象与定位

家长原话：「另外 设置了名字。再选择头像，名字就清除了。这个 BUG 没修复。」

查下来是**同一段代码里的两个毛病**，都在设置页昵称的落盘上
（`src/features/settings/SettingsPage.tsx`）：

| # | 毛病 | 后果 |
|---|---|---|
| ① | 昵称**只在失焦时**保存（`onBlur={commitName}`） | 打完名字**直接点头像**，那一下 tap 不保证先让输入框失焦 → 名字压根没存；而输入框还显示着新名字，**看着像存上了**。下次进设置页 `useState(settings.childName)` 重新初始化 → 名字回到旧的 = 家长看到的「名字没了」 |
| ② | 落盘前**没有空值保护**，`nameDraft.trim()` 原样写入 | 清空输入框再失焦 → 存档里留下 `''` → 在 `{childName} · 三年级`、`XX 的森林` 里渲染成**一片空白**。这才是「名字被清除」的字面来源 |

### ★ 复现靠单元测试，不靠猜

先在 `SettingsPage.test.tsx` 里跑三条探针，把真实行为打出来（不是推断）：

- 打完名字**不失焦**直接点头像 → `store.childName` 仍是 `小笔苗`，但输入框显示 `豆豆`
  → **看着对、其实没存**（这条最阴，光看界面永远发现不了）
- 打完名字 → 失焦 → 点头像 → `豆豆` ✓（原路径本来就是好的）
- 清空输入框 → 失焦 → `''` ← **名字被写成空串**

⚠️ **jsdom 里点击按钮不会让输入框失焦**，所以第一条在测试里天然复现；
真机上的时序（pointerdown → blur → click）反而**可能**是对的 ——
这正是家长报「有时行有时不行」的根源：**它取决于那一下 tap 有没有先触发失焦**。

### 修法（家长定的两条）

1. **空昵称 → 回到「小笔苗」**（和引导页「不填也行，那就先叫小笔苗」同一条规则）
2. **边打边存 + 点头像也存**（不再依赖失焦）

### ★ 顺手把默认名收成一份常量

「小笔苗」原本在**三处**各写一遍：`db.ts` 的 `defaultSettings()`、
引导页的兜底、设置页的兜底。加第三处等于制造漂移
（项目自己的规矩：同一字符串写三遍 = 迟早漂移，见 MEMORY §四/§七）。

现在只有一份：`src/domain/types.ts` 的 **`DEFAULT_CHILD_NAME`**，
`db.ts` / `Onboarding.tsx`（含 placeholder 和提示文案）/ `SettingsPage.tsx` 都引它。

### 验证

- 新增 `src/features/settings/SettingsPage.test.tsx`，**7 条**：
  ①不失焦点头像名字要存 ②先失焦再点（对照组）③清空不留空串 ④只打空格算没起名
  ⑤连点几个头像名字都在 ⑥组合扫描：任何操作后名字都不许是空串 ⑦改名字不弄丢头像
- ★ **变异验证**（临时脚本 `_mutate-name.mjs`，验完已删）：
  · M1 还原「边打边存 + 点头像也存」→ **红 5 条**（对照组仍绿）
  · M2 还原「空值兜底」→ **红 3 条**
  · 两个变异各自红在**该红的那几条**上 —— 判据真能分辨，不是空断言
- ⚠️ **踩坑**：这个仓库的文件是 **CRLF**（1180 个 `\r\n`、0 个裸 `\n`）。
  变异脚本里按 `\n` 写的多行匹配串会「看着一模一样却命中 0 处」。
  脚本改成先归一成 `\n` 再比、写回时还原 CRLF —— 否则一次变异会把整个文件
  的换行符全改掉，diff 变成一千多行。
- `npm run lint` → **0 error / 8 warning**（基线）
- `npx vitest run` → **33 files / 693 passed + 10 skipped = 703**
  （原来是 32 files / 686 passed + 10 skipped）

### ⚠️ 包内校验加不进这一条

`scripts/_verify-apk.mjs` 的 `FEATURES` 表是按**特征串**匹配的，
而这次修复**没有新的用户可见文案**，`小笔苗` 这个值在包里本来就到处都是 ——
凑不出可靠特征。已在那个文件的注释里写明这类改动靠单元测试守，
**不是漏了**，免得下次有人以为要补。

## 二、修「背诵完点领取奖励，回到的页面不对」（家长报）

家长原话：「现在的版本 非常好。就是背诵完 点领取奖励。好像回到的页面不对，
还是在当前写的。是不是不合理。」

### 根因：用错了 `reset` 的分支

`ComposePage` 的 `reset(backToSetup = true)` 有两个分支：

| 参数 | 行为 |
|---|---|
| `true`（默认） | 回出题页，清掉当前题目 |
| `false` | **同一个题目 `beginWith(prompt)`** → 新建一篇空白稿、直接进写作页 |

背诵那一步传的是 **`reset(false)`**：

```
背诵 → 领取奖励 → reset(false) → beginWith(同一个题目) → 新建空稿 → 写作页
```

孩子看到的：一句「背诵奖励 +N 金币」的提示，然后**一篇同名的空白作文**。

### ★ 两个佐证（说明这是误用，不是设计）

1. **`reset(false)` 全项目只用了一次** —— 就是背诵这里。
   其他所有出口（点评页的「回到出题」、离开确认、`handleBack`）都用 `reset()`。
2. **注释里说的那个「再写一篇」按钮根本不存在** —— `grep 再写一篇` 只命中
   `reset` 自己的那段注释。也就是说 `false` 这一支实际上只为背诵那条路而存在，
   而它的注释却在为一个不存在的按钮辩护。

### 修法（家长定：回到出题页）

- 调用点改成 `reset()`。
- ★ **按家长要求，把 `backToSetup` 参数和 `false` 那一整支删掉了**。
  理由：它现在**零调用者**，留着就是"下次又有人传 false"的地雷；
  删掉之后**全流程的出口只剩一种**，"选错出口"这类 bug 结构上不可能再犯
  —— 这比加一条测试更硬。要恢复"同一题目再写一篇"，得先有真的按钮。
- 顺带把调用点那段长注释收短（细节收在 `reset` 上）——
  同一件事写两遍迟早漂移。

### 验证

- `npm run lint` → **0 error / 8 warning**（基线）
- `npx vitest run` → **33 files / 693 passed + 10 skipped = 703**（与改前一致，没有回归）
- ⚠️ **没加自动化测试，原因说明**：这条 bug 在**接线**上（哪个回调传给了 `ReciteView`），
  而 `step` 是 `ComposePage` 的内部 state，没法从 store 直接播种；
  要走到背诵步得完整驱动 写 → 点评 → 写法 → 背诵 四步，
  而写作台的正文**只能靠语音输入**（`VoiceComposer` 里没有正文输入框），
  在 jsdom 里要额外 mock 识别器 —— 成本高且脆。
  所以选了**结构性修复**（删掉分支）而不是测试。
