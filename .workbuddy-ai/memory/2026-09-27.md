### 7.3 ★★ 两个"不报错就错"的坑，都做了守卫

**① id 串位**：内置 id 是 `builtin-<标签>-<序号>`，序号来自 `forEach((tpl,i)=>i+1)`。
往数组**最前面**插一条模板 → 后面每条 id 平移 → 覆盖层里那句 `lead`
会**安安静静盖到另一道题上**。
➜ 每条覆盖都存 `baseTitle` / `baseLead`（改的时候的原文），
`checkLibraryOverrides()` 每次对一遍，**对不上就报"可能被挪位了"，不照盖**。

**② 空覆盖层让测试变成装饰**：盘上那份现在是 `{}`，
所以"空覆盖 ⇒ 输出跟底稿逐字节一样"这条**不管合并没有接线都通过** ——
把 `applyLibraryOverride` 那行删掉，整套测试依然全绿。
➜ 给 `buildBuiltinLibrary(overrides?)` 开了一个**只给测试用的口子**，
塞一份**非空**假覆盖进去，看输出真的变。
➜ **变异验证过**：把合并改成 `return item` → 恰好 3 条（"塞假覆盖"那三条）变红，
而"空覆盖 ⇒ 一样"**照样绿** —— 当场证明后者是装饰。

### 7.4 配图为什么是"逐张补位"而不是"整组替换"

`SceneArt` 的优先级本来就是 `题目 imageUrl` → 注册表 → **SVG**。
➜ 覆盖层**只往 `images[k].imageUrl` 里填地址，`sceneKey` 一个字不动** ——
外链挂了还能退回插画（`docs/library-data-guide.md`：「重要的题建议两个都填」）。
⚠️ 只能**从第一张起连着换**（不能跳着换）→ 编辑页把"第一张空着"后面的槽位**锁住**，
否则会写出 `[null,null,"https://…"]` 这种带洞数组（正是校验要报的错）。

- `checkLibraryOverrides(overrides, base)` —— 要底稿：id 存不存在、baseTitle 对不对得上、配图有没有给多。
  ⚠️ 端点**故意不做**这几条（它不去加载 136 条底稿），同 `validateIntros` 不查地标存在与否。

### 8.2 ★★★ 这一版真正的坑：iframe 的 `beforeunload` 弹不出对话框

两个子页原来各自有 `beforeunload` 守卫。**嵌进 iframe 之后它就废了** ——

这正是本项目最怕的那一类（不报错、不崩、只是东西没了）。

➜ 修法：子页**把状态报上去**，父页汇总起来守。
- 子页：`{ type: 'lw-tool-dirty', tool: 'travel' | 'library', dirty }` postMessage 给 `window.parent`。
- 父页：`beforeunload` 里任一工具脏 → `preventDefault()`。
- ★ 子页嵌进去时**主动让自己的 `beforeunload` 变哑**（`if (EMBEDDED) return`）——
  留着它只会让人以为"已经守住了"。

## 10. 批量给内置题配外链图（31 道，覆盖全部 5 个大类）

家长：**「再帮我添加一些，各类的。写人，写景，tag 也可以自由添加。随你。」**
→ 我先只做了写景 6 + 写人 5，家长立刻纠正：**「不只是 写景，写人 还有其他场景吧。」**
（**教训**：家长说"各类的"就是"五类都要"，别把"写人/写景"当成范围，那只是**举例**。）

### 10.1 ★★★ 最大的坑：**Pexels 的结果大多数是竖图，而这个框会把竖图砍掉一半**

`SceneArt` 渲染外链图时是 **`aspect-ratio: 4/3` + `object-cover` + 居中**（`scenes.tsx:6691`）。
竖图（0.67）在这个框里**只保留中间 50% 的高度** —— 星空会只剩中间一条、蹲着的人会被裁掉头。

**实测：45 张候选里 29 张是竖图（64%）。** 不是个别现象，是默认情况。
➜ **顺序必须是「先量宽高比、再挑图」**，不是"挑完再看"。
量法：**下载后用 JPEG SOF 段读真实像素**（`0xC0/0xC1/0xC2`）；
`?w=640` 是等比缩放，宽高比不变。
判据：**ar ≥ 1.33 才安全**（4:3 正好不裁）；1.15~1.33 丢 ≤13%；**< 1.15 直接弃**。

⚠️ 反面教训：第一轮我按"标题 + 内容像不像"挑完 15 张，**量完尺寸发现 5 道题一张横图都没有**
（秋天的落叶 / 下雨了 / 日落 / 奶奶织毛衣 / 图书管理员 全是竖图）→ 白挑一轮，只能重搜。
**"挑之前先量"能省掉一整轮返工。**

### 10.2 ★★ 45 张怎么看：**拼联系表，别一张张 Read**

用 `puppeteer-core` + `page.setContent()` + data URI 拼 5 列网格，`page.screenshot({fullPage:true})`。
**45 张 = 3 张 PNG**（每张 15 格）。⚠️ 用 data URI 是因为 `setContent` 的源是 `about:blank`，
**`file://` 图片会被挡**。
★ 顺手让格子的 `img` 就用 **`320x240` + `object-fit:cover`** ——
**联系表本身就是"4:3 裁切后的样子"**，一眼就能看出竖图被裁成什么样。这一步免费。

### 10.3 ★★ 挑图的两个额外判据（比"好不好看"重要）

1. **先读这道题内置插画的 `hint`**（`scenes.tsx` 的 `SCENES` 数组里，`key → hint`）。
   hint 写的是插画画了什么，照片要跟它**同色系 / 同要素**：
   - `autumn-leaves` hint「满地金黄的落叶铺在**小路**上」→ 挑"小路 + 金黄落叶"，不是随便一堆叶子
   - `dad-repair` hint「爸爸蹲在**倒放的自行车**旁，手里拿着扳手」→ 要**修自行车**，
     我一开始按"爸爸修东西"搜了"工具箱/工作台"，**全不对**
   - `bus-driver` hint「一辆**黄色**公交车…司机坐在方向盘后面」→ 我第一轮挑的绿白车还带外文站牌
   ➜ **搜关键词要用 hint 里的具体物件，不是题目的抽象标题。**
2. **`SceneArt` 对「题自带的外链」故意不加暖色滤镜**（只有 `SCENE_IMAGES` 里 `style:'photo'` 的加）
   → 真照片天生比周围卡通插画**偏冷**。挑**暖调**（晨光/夕阳/暖木色）能少一点违和。

### 10.4 数据落盘 + 三条验证

- 31 条：写景 6 / 写人 6 / 状物 7 / 写事 6 / 想象 6（**五类都有**）。
- **用脚本生成 JSON**（Python：`sorted(keys)` + `indent=2` + `ensure_ascii=False` + 结尾换行）
  → 跟 `normalizeLibraryItems()` 的规范形**逐字节相同**（有断言：`canon === raw` → true）。
  ⚠️ 31 条手写键序**一定会错**，让程序排序。
- ① `libraryItems.test.ts` **39 passed**（读盘上文件 → 顺带证明 id 存在 / 锚对得上 / 地址合法）
- ② 字节幂等：`canon === raw` → **true**（家长第一次点保存不会整份重排）
- ③ ★★ **渲染链路探针**（一次性脚本，跑完已删）：同源页里 `import('/src/domain/builtinLibrary.ts')`
  调**真代码** → `buildBuiltinLibrary()` = 136 条 / 31 条带外链；再 `new Image()` 真解码：
  **31/31 成功**，宽高比 **1.31 ~ 1.78（全横图）**。
  ★ 这一步是数据层证明不了的 —— 「JSON 多了 31 条」和「孩子能看见 31 张图」长得一模一样。

### 10.5 ★★ 顺手抓到一条**过时脚本**（不是我改坏的）

`_verify-library-import.mjs` 崩在 `waitForFileChooser` 超时。**判定过程值得记**：
- 它第 248 行硬断言「**题库还是空的**」；而 `useApp.ts:414` 每次启动
  `reconcileBuiltinLibrary()` 会把 **136 道内置题并进孩子的题库** → **这句永远不可能成立**。
- 它 grep 全文 **0 处**引用 `library-items.json`。
- **决定性一步**：把数据换成**开工前那份 1 条**（md5 `c5f76a21…`）**复跑 → 一模一样地崩**。
  ➜ **过时脚本，跟本次改动无关**。之后已还原（md5 回到 `c5df2f34…`）。
★ 一般化：**「我改完它红了」要先问「它红的那个前提今天还成立吗」** ——
  前提已经不成立的老脚本，红得跟"我弄坏了"一模一样。

## 12. 家长看了图之后的三条反馈（两条是真缺陷，一条是设计使然）

家长原话：
> 「为什么有些图是一样的。是不是因为拉的图的没随机，都选择了第一个。
>   还有某些图 说了是彩虹却没彩虹。 说了谁织毛衣 但是没见到人。」

### 12.1 (a) 图一样 —— **不是没随机，是按 `sceneKey` 共用**

一条 `sceneKey` 只配一张图，**所有用到这个 key 的题共用同一张**（这是设计，不是 bug）。
再加上 Phase B 我给新题**复用了已配过的 key**（`all-kinds-people` / `future-me` /
`doctor` / `wheat-field` / `sunset` / `river-village`）→ 共用更多。

实测：**113 条 / 131 个槽位 / 去重后 103 个地址 / 25 个地址被 48 道题共用**。
最大的三组：`35521703`×3（文化-1、文化-2、游记-2）、`6162307`×3、`8954779`×3。

★ 家长猜的"都选了第一个"**不成立** —— 子代理是按 key 各搜各的；
  共用完全由 `sceneKey` 决定。要不要拆开（一题一图）是**产品决定**，已报告等家长定。

### 12.2 (b) 彩虹没彩虹 —— 卡片缩略图取的是 `images[0]`

`雨后的彩虹`(`builtin-weather-2`) 的 `scenes` 原来是 `['rain-window','rainbow']`，
第 0 张是**雨窗**照片 → 卡片上**永远看不到彩虹**。
（卡片取 `images[0]`：`library-browse.html:452`、`ComposePage.tsx:814`。）

**★★ 修的时候发现 `sceneKey` 不是死字段**，所以不能只翻 `imageUrls`：
- `scenes.tsx:6680` → `sceneKey` 被当成图片的 **alt**
- `imageHints.ts:48` → `sceneKey` 用来拼**发给 AI 的画面描述**
- 只翻 `imageUrls` 的话，第 0 张会变成「`sceneKey=rain-window` 却是一张彩虹照片」→ 悄悄错
➜ **两处一起翻**：`prompts.ts` 的 `scenes` 改成 `['rainbow','rain-window']` + 覆盖层 `imageUrls` 同步翻转。
安全：scenes 顺序**不影响 id**（id 只看模板在数组里的下标）；`allTemplateScenes()` 是 Set；
测试只钉 caption 的**形状**（`第 N 幅`）不钉帧数。
顺序翻转也不违背原文：lead 开头就是「雨停了」，第 1 幅给彩虹才是当下发生的事。

### 12.3 (c) 织毛衣没人 —— **是我自己的作业规则害的**

`scripts/_photo-scene/README.md` 里我写的是：
> 「项目约定：不画人脸 —— 有人物时优先背影/远景/不露脸，**宁可挑"只有物件"的那张**」

子代理老老实实照做 → 挑回「毛线团 + 一根棒针，一个人都没有」。
**规则错在**：它把"避免正脸"写成了"宁可选物件"，而
**题目名字本身就是一个人的时候，物件代替不了人**。
（而且 `8954779`「有人脸」的照片**早就已经上库了** → "不画人脸"从来不是硬约定。）

★★ **§10.7.5 我当时「如实报、不糊」地报了这两张缺人，然后照样发了货 —— 家长转头就自己发现了。
"报备过"不等于"可以不修"。配图缺了题目点名的主体 = 缺陷，不是取舍。**

### 12.4 顺手把同一类查全了：17 个「题目名字就是人」的 key

写了 `scripts/_photo-scene/audit-person.py`：把 `prompts.ts` 的 `PROMPT_TEMPLATES`
× `scenes.tsx` 的 `SCENES` × 覆盖层拼起来，**按「标题是不是一个人」筛**（hint 里提到人只能算弱信号：
`太空旅行`/`堆雪人` 的 hint 也有「小人」，但配图是火箭/雪人，**没有人才对**）。

17 个 key 拼成一张联系表逐个看 → **除家长点名的 2 处，又抓到 2 处同类**：
- `bus-driver` 公交司机 → 原图是**空车厢**（一个司机都没有）
- `librarian` 图书管理员 → 原图**只有书架**（管理员阿姨不见了）
其余 13 个都有主体（`robot-friend`/`sewing-box` 是**物件**，本来就该没有人才对）。

⚠️ 中途我自己看错一张：把 `cactus-1903974` 说成"空白粉墙"，重看是**一盆仙人掌**，是**对的**。
★ **联系表要放大看**，320×240 的格子容易把主体认错。

### 12.5 ★★★ 最有价值的一招：搜图时加 `?orientation=landscape`

前面 18 张织毛衣候选里只有 4 张横图（`1/10`）—— 因为**默认搜索结果七成是竖图**。
这次在 URL 上加 **`?orientation=landscape`**：
- `librarian` → 7/7 横图
- `bus driver` → 7/7 横图
- `grandmother knitting` → 6/6 横图

**命中率 100%（对比 1/10）。** 这比"下回来再量、再筛"省掉整个筛选环节 ——
**应该是最先做的一步**，不是量完再补救。

### 12.6 ★★ 宽高比门槛是**代理指标**，联系表才是真相

`36456379`（奶奶织毛衣第二轮）ar = **0.75**，按门槛"直接丢"。
但它是**竖图里主体坐在中下带**：上面 40% 是墙 → 4:3 居中裁保留中间 56%，
**正好把头 + 手 + 毛线全留下**。我按门槛判它是废的，**联系表（= 裁切后的样子）证明它可用**。
➜ 门槛用来**排序和预警**，最终判据永远是"按目标比例裁完还剩下什么"。
（这次没选它，是因为 `5585242` 更好：老花镜 + 毛线团，跟 hint 严丝合缝。）

### 12.7 ★★ 解析 `prompts.ts` 踩的坑：**正则只认出一部分，数字还挺合理**

第一版正则 `^\s*'([a-z0-9-]+)':\s*\[\s*$` 只匹配**带引号**的 tag 名，
于是只认出 **10 个 tag / 29 条模板**（真实是 **41 / 144**）。
两个坑叠在一起：① 这文件里 `season:` 不带引号、`'home-scene':` 带引号；
② 有的模板条目**跨多行**（`title`/`lead`/`scenes` 各占一行）。
⚠️ **最危险的是它没报错，而且 29/10 这个数字看着不荒谬** → 差点按漏了一半的清单去做审计。
➜ 修法：tag 头用 `'?([a-z0-9-]+)'?`，条目用 `title:…[\s\S]*?scenes:[…]` 非贪婪跨行配。
★ 一般化：**解析自己的源码时，先打印总数跟已知常量对一下**（144 / 41 是已知的），对不上就是解析错了。

### 13.3 ⚠️ 顺手发现：编辑器**没法把一道题退回插画**

`src/domain/libraryItemRules.ts:140-155`：
